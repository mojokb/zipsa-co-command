# v0.0.5 Roadmap: Skill Enhancement Plan

## Background

This document captures the planned improvements for v0.0.5, derived from an analysis of
reference skill patterns in a separate skills repository. The improvements address three
gaps in the current skill set:

1. **zipsa-tasks** lacks a human-vs-agent classification, making it unclear where autonomous
   execution should pause for human decisions.
2. **zipsa-review** only evaluates code quality — it has no axis for whether the code
   actually implements what was asked for.
3. **zipsa-plan** and **zipsa-validate** are unaware of previously recorded architectural
   decisions (ADRs) and project domain vocabulary (CONTEXT.md), which risks re-litigating
   settled decisions across sessions.

---

## Impact on Workflow Relationships

The current workflow is a linear pipeline:

```
zipsa-think → zipsa-plan → zipsa-validate → zipsa-tasks → (zipsa-build) → zipsa-review
```

After v0.0.5, three structural changes emerge:

**1. Branching after zipsa-tasks (HITL/AFK)**
```
zipsa-tasks
  ├── AFK tasks → zipsa-build (autonomous)
  └── HITL tasks → human decision → back to zipsa-plan or zipsa-validate
```

**2. zipsa-review gains backward dependencies**
```
zipsa-plan → [plan.md] ──────────────────────┐
zipsa-tasks → [tasks.md] ────────────────────┤
(zipsa-build) → code ────────────────────────┤
                                              ↓
                                    zipsa-review (Spec axis)
```

**3. Shared project artifacts emerge**
```
zipsa-plan ──read/write──┐
zipsa-validate ──────────┤──→ [CONTEXT.md, docs/adr/*.md]
zipsa-plan (next session)┘         ↑
                                  read (prevents re-litigation)
```

## Planned Changes by Skill

### 1. zipsa-tasks — HITL/AFK Classification + Vertical Slices

**Priority:** High | **Overhead added:** Low

**Problem:** Tasks are produced as an undifferentiated list. There is no signal for which
tasks an agent can execute autonomously vs. which require a human decision before proceeding.
The current breakdown also tends toward horizontal slices (e.g. "write all DB schema", then
"write all API endpoints") rather than thin vertical slices that are independently demoable.

**Changes to `SKILL.md`:**

- **Description**: add "Each task is classified as HITL (requires human) or AFK (agent can
  proceed autonomously)."
- **Step 2 (Ambiguity resolution)**: when evaluating each resolved decision, note whether
  it implies a HITL or AFK task downstream.
- **Step 3a (Your own task breakdown)**: add vertical slice principle — each task must cut
  through all relevant layers end-to-end and be independently verifiable. Add HITL/AFK field
  per task.
- **Step 3b (Codex prompt)**: request HITL/AFK classification and vertical slice structure
  from Codex.
- **Step 4 (Compare and merge)**: add HITL/AFK conflict resolution rule — when one side
  says HITL and the other says AFK, default to HITL (safer).
- **Output Format**: add `**Type:** HITL / AFK` and `**Verifiable by:** [how to confirm
  this task is done without running subsequent tasks]` fields per task.

**Vertical slice rule to add:**

> Each task must be a thin slice that cuts through all relevant layers (data, logic, interface)
> and produces something independently verifiable. Avoid horizontal slices that implement
> one layer in full before touching the next.

### 2. zipsa-review — Spec Axis

**Priority:** High | **Overhead added:** Medium (requires plan.md or spec source)

**Problem:** zipsa-review evaluates code quality (SOLID, Clean Code, docstrings, lint) but
has no axis for whether the code implements what was actually requested. A codebase can be
perfectly clean while implementing the wrong thing.

**Changes to `SKILL.md`:**

- **Description**: add "Two-axis review: Code Quality (SOLID, Clean Code, lint, docstrings)
  and Spec Compliance (does the code match the originating plan or issue?)."
- **New Step 0 — Identify spec source**: before spawning Codex, look for a spec in this
  order:
  1. `plan.md` or `tasks.md` from the current session (check conversation context)
  2. A file path passed as a second argument
  3. Issue references in recent commit messages
  4. If none found, note "Spec axis skipped — no spec available" and continue with
     Code Quality axis only.
- **Step 1b (Codex prompt)**: add Spec axis instructions — Codex reviews against the spec
  source, flagging: (a) requirements missing or partially implemented, (b) behaviour present
  in code that was not asked for (scope creep), (c) requirements that appear implemented
  but look wrong.
- **Step 2 (Your own review)**: add Spec axis review instructions alongside the existing
  Code Quality review.
- **Step 3 (Merge)**: keep the two axes separate in the output — do not merge them.
- **Output Format**: add `## Spec Compliance` section with three subsections:
  - Missing / partial requirements
  - Scope creep (unrequested behaviour)
  - Likely wrong implementations

---

### 3. zipsa-plan — Domain Awareness + ADR Offers

**Priority:** Medium | **Overhead added:** Medium (lazy — only when files exist)

**Problem:** Each zipsa-plan session starts from scratch. If the project has a domain
glossary (CONTEXT.md) or recorded architectural decisions (docs/adr/), the plan may
contradict settled terminology or re-litigate decisions that were already resolved.

**Changes to `SKILL.md`:**

- **New Step 0 — Read project context (lazy)**: before spawning Codex, check for:
  - `CONTEXT.md` at the repo root — if found, read it; use its vocabulary throughout
    the plan and flag any terminology conflict with the user's request
  - `docs/adr/*.md` — if found, skim titles and summaries; do not propose approaches
    that contradict an existing ADR unless the friction is significant enough to warrant
    reopening it (mark clearly if so)
  - Pass relevant excerpts to Codex in its initial prompt
- **During plan generation**: when a significant architectural decision is made (technology
  choice, integration pattern, scope boundary), note it as an ADR candidate.
- **Output section**: add `## ADR Candidates` to the saved plan file, listing decisions
  that meet the three criteria: (1) hard to reverse, (2) surprising without context,
  (3) result of a real trade-off. Do not create the ADR files — flag them for the user
  to confirm.

**ADR creation criteria to embed:**

> Only flag a decision as an ADR candidate when all three are true:
> 1. Hard to reverse — meaningful cost to change later
> 2. Surprising without context — a future reader would wonder "why this?"
> 3. Result of a real trade-off — genuine alternatives existed

### 4. zipsa-validate — Domain Awareness + ADR Re-litigation Prevention

**Priority:** Medium | **Overhead added:** Low (builds on zipsa-plan's context read)

**Problem:** zipsa-validate reviews a plan without checking whether the plan's terminology
aligns with the project's existing domain model, or whether it proposes reversing decisions
already captured in ADRs.

**Changes to `SKILL.md`:**

- **Step 1 (Read plan + spawn Codex)**: add domain context read — same as zipsa-plan Step 0
  above. If CONTEXT.md exists, check the plan's terminology against the glossary and note
  conflicts. If ADRs exist, check the plan does not contradict them.
- **Step 2 (Your own review)**: add two new review dimensions:
  - **Terminology alignment**: does the plan use terms consistently with CONTEXT.md?
    Flag any term that is used differently or that is missing from the glossary.
  - **ADR conflicts**: does the plan propose reversing or ignoring an existing ADR?
    If so, is the reason strong enough to warrant reopening it?
- **Codex prompt addendum**: instruct Codex to apply the same two dimensions.
- **Output / Step 3**: when accepting a plan change that settles a terminology question or
  reverses an ADR, note it explicitly as requiring a CONTEXT.md update or ADR update.

---

### 5. zipsa-think — Interactive Grilling Mode (Optional)

**Priority:** Low | **Overhead added:** Low

**Problem:** zipsa-think only offers a parallel brainstorming mode (agent and Codex work
independently, then compare). There is no interactive mode where the user is questioned
one-by-one to stress-test their own thinking.

**Changes to `SKILL.md`:**

- **New mode detection**: if the argument starts with `--grill` or the user's request
  contains "grill me" / "질문해줘", switch to interactive mode.
- **Interactive mode**: ask one question at a time, provide a recommended answer, wait
  for user response before continuing. Walk down the decision tree, resolving dependencies
  between ideas one by one. Codex background subagent still runs in parallel.

## Implementation Order

Dependencies constrain the order:

```
Phase 1 (independent)
  └── zipsa-tasks: HITL/AFK + vertical slices

Phase 2 (zipsa-plan must precede zipsa-validate)
  ├── zipsa-plan: domain awareness + ADR offers
  └── zipsa-validate: domain awareness + ADR prevention

Phase 3 (depends on plan.md artifact being reliable)
  └── zipsa-review: Spec axis

Phase 4 (optional, low priority)
  └── zipsa-think: interactive grill mode
```

Recommended sequence: Phase 1 → Phase 2 → Phase 3 → Phase 4.
Each phase can be released independently as a patch version.
